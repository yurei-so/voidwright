## Root cause and correction

The first diagnosis identified the need to retry unresolved entity lookups, but candidate-k showed why the new retry policy still stopped immediately. At its first mod preflight sample (`2026-10-19T16:18:04.2477807Z`), controller/grid/camera were `0/0/0`, speed was `NaN`, and the operator state was unavailable. Those checks were `UNKNOWN`, but `BuildPreflight` computed `safety_configuration` as `FAIL`: the old expression treated `operatorFree == false` as a definite failure even when the controller did not exist. `PreflightOnlyPolicy` correctly terminates on a definite failure, so it wrote `preflight-blocked` at elapsed tick 0 and set `terminal=true`. `ResolveEntities` and `PublishHeartbeat` therefore never got another update. `PublishHeartbeat` also returns without writing unless controller and camera have resolved, so the absent heartbeat and host `FileNotFoundException` were downstream symptoms, not evidence of a filename mismatch.

Safety status now stays `UNKNOWN` until the context, controller, and speed are observable; it becomes `FAIL` only for a known unsafe configuration/operator state and `PASS` only when all those observations are safe. The `preflight-only` branch retries while required evidence is unknown, writes progress evidence on the existing 60-tick cadence, stops on a definite failed check, and completes only when all ten checks pass and the host has approved the fresh run-bound heartbeat. The existing operation deadline still bounds the retries. It returns before the actuator dispatch gate in every outcome.

The saved log does not establish why the first ModAPI lookup returned no controller or camera. An entity-registration delay remains possible, as does a persistent lookup/API limitation. The offline correction removes the proven premature terminal condition; it does not prove that the public ModAPI lookup will eventually resolve the entities.

## Offline repair of the preflight-only terminal lifecycle

Candidate-n exposed a second lifecycle defect. The server plugin treated `preflight-only` as a continuing mod-owned depth operation: after the mod had emitted its one-shot 10/10 completion and the host had approved the exact heartbeat, the plugin kept polling. At 3,600 ticks it emitted `type=depth-controller status=timeout`; the receipt parser allowed that different event type to replace the completed preflight event. In parallel, the host wrote each result over one canonical JSON path, so its post-terminal stale 6/10 poll replaced the earlier 10/10 snapshot.

The plugin now ends a `preflight-only` operation as soon as the exact fresh mod heartbeat is host-approved and its full preflight authorizes, emitting a host-confirmed `type=preflight-only status=complete` terminal event with `actuatorDispatch=none`. If that handshake does not pass before the configured deadline, the plugin emits `type=preflight-only status=timeout`; the timeout remains terminal and unsuccessful. The worker receipt parser treats only `preflight-only` events as authoritative for a `preflight-only` action, so an unrelated enclosing depth-controller deadline cannot overturn its one-shot result. Each host result is now archived under `Quarantine/<run>/movement-preflight-snapshots/` with run, operation, and UTC timestamp in the name before the existing latest-view JSON is atomically updated.

Offline regression coverage exercises the real receipt parser with the candidate-n ordering (preflight completion followed by a 3,600-tick depth-controller timeout), verifies that an explicit preflight-only timeout remains a failed terminal result, and tests the real host snapshot writer with two different records to prove the first is retained while the latest view advances. No fixture was launched during this repair. Validation: Voidwright Core **63/63**; VRageCage worker script suite passed, including CLI wait and receipt policy tests; server plugin compile check passed with 0 warnings/errors; game-target mod build passed with 0 warnings/errors; `git diff --check` passed.

### Separate geometry-veto policy

The stricter policy requires the same score threshold and geometry result zero.
It was not separately recalibrated on the test set. It can reduce false-safe
counts and coverage while increasing the error fraction among the remaining
permissions. Front test: 28/967 = 2.90% hazardous, compared with 36/1,935 = 1.86%
for the broader learned decision. The veto alone does not meet the target.

## Inspected failures and camera loss

The first front point-model checkpoint's actual retained test errors include
four overhang cases, two trenches and one wall. The seven have geometry result
zero and learned scores below 0.24, so both the model and baseline miss them.
The full-depth mosaic shows nearby ground with much of the hazard outside the
observed support. Occlusion is an interpretation; the image, oracle label and
scene parameters remain available for precise follow-up. The report does not
claim every error is an impossible perception problem.

Dropping FRONT from front-only runs produces no permissions. Dropping an already
missing role leaves that run unchanged. Random-camera losses retain some
permissions and can change scores; removing information need not monotonically
increase a neural score. The separate controller loss latch blocks new motion
candidates until explicit replanning. It grants no model authority.

### Export and performance status

r7/r8 export checks retained failures rather than accepting changed scores.
Front case 27 had eager logit 10.00705814 versus TorchScript 10.00722599, exceeding
the preregistered absolute 1e-4 tolerance. CUDA graph replay matched eager exactly
on that case. This is a numerical backend difference; it is not evidence of a
changed driving decision on that case. r9 qualifies each backend independently
under the unchanged tolerance and records full score/decision differences.
Final r10 measurements materialize compressed arrays once outside timing.
r9's roughly 101 ms host-path timing included repeated NPZ inflation and is
superseded for resident-tensor latency; it was not a 100 ms geometry computation.
No model or threshold was changed by that measurement correction.

Both CUDA captures match all 1,280 logits exactly and preserve every threshold

CUDA graphs are constructed in-process from pinned model weights and static
buffers; the TorchScript file is not a serialized CUDA graph.

In these 256-case benchmark subsets, camera removal created no **new geometry-
guarded** candidates. That is a limited sample result, not a general monotonicity
proof or a demonstration of the latch rescuing a newly dangerous candidate.
The controller latch's role-loss/recovery logic is separately unit tested. Both
loadouts reject malformed available depth and abstain with all cameras missing.
The host path above excludes game capture/transport/controller provenance,
physics and actuation. It is not end-to-end game latency.

## Reproduce the analysis

From this source directory, run `analyze.py` on the retained `front-matrix-v4` and
`multicam-matrix-v4` directories with a fresh output directory. It verifies hashes,
recomputes counts, and checks paired inputs before writing JSON/CSV/plots.
`report.py` reads retained inputs/predictions and never calls a model. See the
README for the input contract and operations for exact private paths and gates.
